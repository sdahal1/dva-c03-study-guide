# 2.2.5 Generate certificates and SSH keys for development needs

**Domain 2 · Task 2.2 · Skill 2.2.5** · [Task overview](README.md) · Previous: [2.2.4 KMS key management](2.2.4-kms-key-management.md) · Next: [2.2.6 Sensitive data detection and masking](2.2.6-sensitive-data-detection-and-masking.md)

## What the exam expects

Developers routinely need a key pair to reach an EC2 instance, a TLS certificate for local HTTPS, or a client certificate to test mutual TLS (mTLS). This skill is lighter than the rest of Task 2.2. Expect questions on creating and importing EC2 key pairs, generating self-signed certificates and certificate signing requests (CSRs), where self-signed certificates are accepted, and the AWS options that avoid distributing long-lived SSH keys at all.

You must be able to:

- Create SSH key pairs with `ssh-keygen` or EC2 key pairs, import a public key, and protect the private key.
- Prefer Session Manager or EC2 Instance Connect over shared, long-lived SSH keys.
- Generate a self-signed certificate and a CSR with OpenSSL, and know where each is accepted.
- Get realistic private certificates for test environments from AWS Private CA.
- Store development private keys safely, outside source control.

## Key terms

| Term | Meaning |
|---|---|
| Secure Shell (SSH) key pair | A private key you keep and a public key placed on the server (`~/.ssh/authorized_keys`). Authenticates SSH logins. |
| EC2 key pair | An SSH key pair registered with EC2. AWS stores the public key and injects it into new Linux instances. |
| Self-signed certificate | A TLS certificate signed by its own private key. No CA vouches for it, so clients warn unless told to trust it. |
| CSR | Certificate signing request. Contains your public key and subject, sent to a CA to get a signed certificate. |
| Subject Alternative Name (SAN) | The hostnames a certificate is valid for. Modern browsers check the SAN, not the common name (CN). |
| PEM | Base64 text format for keys and certificates (`-----BEGIN CERTIFICATE-----`) |

## SSH keys

### Generate locally

```bash
# ED25519 is short and modern; RSA 4096 for systems that need RSA
ssh-keygen -t ed25519 -C "dev@example.com" -f ~/.ssh/dev-ed25519
ssh-keygen -t rsa -b 4096 -f ~/.ssh/dev-rsa

chmod 400 ~/.ssh/dev-ed25519      # ssh refuses private keys readable by others
```

### EC2 key pairs

| Action | Command | Notes |
|---|---|---|
| Create in AWS | `aws ec2 create-key-pair --key-name dev --key-type ed25519 --key-format pem --query KeyMaterial --output text > dev.pem` | The private key is returned once. AWS keeps only the public key. Lose it and you can't download it again. |
| Import your own public key | `aws ec2 import-key-pair --key-name dev --public-key-material fileb://~/.ssh/dev-ed25519.pub` | The private key never leaves your machine |
| Create with CloudFormation | `AWS::EC2::KeyPair` | A new key pair's private key is saved to Parameter Store as `/ec2/keypair/<key_pair_id>`; read it with `aws ssm get-parameter --with-decryption` |
| Describe or delete | `describe-key-pairs`, `delete-key-pair` | Deleting the key pair doesn't remove the public key from running instances |

- Key types: RSA or ED25519. ED25519 isn't supported for Windows instances. Formats: `.pem` for OpenSSH, `.ppk` for PuTTY.
- For Windows instances, the key pair decrypts the initial Administrator password instead of being used for SSH.
- Lost the private key? You can't recover it. Add a new public key through Session Manager, EC2 Instance Connect, or user data, or detach the root volume, edit `authorized_keys` from another instance, and reattach.

### Avoid distributing SSH keys

| Option | How it works | Network requirement | Exam angle |
|---|---|---|---|
| AWS Systems Manager Session Manager | Browser or CLI shell through the SSM Agent and IAM permissions. Sessions can be logged to S3 or CloudWatch Logs. | No inbound ports, no SSH keys, no bastion. Needs the SSM Agent, an instance profile, and a path to SSM endpoints (VPC endpoints in private subnets). | "No port 22, audited sessions, IAM-controlled" |
| EC2 Instance Connect | AWS pushes a temporary public key to the instance metadata for 60 seconds; you connect with SSH | Port 22 must be open to the source. Preinstalled on Amazon Linux 2 (2.0.20190618 and later), AL2023, and Ubuntu 20.04 and later. | "No long-lived keys, IAM-controlled SSH". Connection failures are usually the security group. |
| EC2 Instance Connect Endpoint | Instance Connect to instances in private subnets without a public IP | Endpoint in the VPC | "SSH to a private instance without a bastion" |

```bash
# Session Manager from the CLI (needs the Session Manager plugin)
aws ssm start-session --target i-0123456789abcdef0

# Instance Connect: push your own public key for 60 seconds, then SSH
aws ec2-instance-connect send-ssh-public-key --instance-id i-0123456789abcdef0 \
  --instance-os-user ec2-user --ssh-public-key file://~/.ssh/dev-ed25519.pub
ssh -i ~/.ssh/dev-ed25519 ec2-user@<public-dns>
```

### Git SSH keys

Git hosts authenticate pushes with SSH public keys or HTTPS tokens. Generate a dedicated key per machine with `ssh-keygen`, upload only the `.pub` file, and never commit private keys.

> **Not on the DVA-C03 service list for new customers.** AWS CodeCommit supports SSH public keys uploaded to an IAM user (`aws iam upload-ssh-public-key`) and HTTPS Git credentials. Give another account access with a role and STS `AssumeRole`, never shared SSH keys.

## Development TLS certificates

### Self-signed certificate for local HTTPS

```bash
openssl req -x509 -newkey rsa:2048 -nodes \
  -keyout key.pem -out cert.pem -days 365 \
  -subj "/CN=localhost" \
  -addext "subjectAltName=DNS:localhost,IP:127.0.0.1"

openssl x509 -in cert.pem -noout -text   # inspect subject, SAN, validity
```

- `-x509` makes a self-signed certificate instead of a CSR. `-nodes` leaves the private key unencrypted, which is fine on a laptop and wrong anywhere shared.
- Browsers warn until you add the certificate to the local trust store. Tools like `curl` need `--cacert cert.pem` (better than `-k`, which disables verification).

### Certificate signing request

```bash
openssl req -new -newkey rsa:2048 -nodes \
  -keyout api.key -out api.csr \
  -subj "/CN=api.dev.example.com" \
  -addext "subjectAltName=DNS:api.dev.example.com"
```

Send the CSR to a CA. With AWS Private CA you can issue directly from it:

```bash
aws acm-pca issue-certificate --certificate-authority-arn "$PCA_ARN" \
  --csr fileb://api.csr --signing-algorithm SHA256WITHRSA \
  --validity Value=30,Type="DAYS"
```

### A dev CA that behaves like production

For test environments that need realistic internal TLS or mTLS, issue certificates from AWS Private CA (shared with RAM across dev accounts) instead of hand-rolling self-signed certificates per service. Clients trust one private root, certificates renew through ACM, and revocation works. Short-lived certificate mode suits throwaway test certificates. Full details in [2.2.2](2.2.2-certificate-management.md#aws-private-ca).

### Where self-signed certificates work

| Place | Self-signed accepted? |
|---|---|
| Your local dev server | Yes, after trusting it locally |
| ALB to targets (HTTPS target group) | Yes. ALB doesn't validate target certificates, so re-encryption with self-signed target certificates works. |
| Importing into ACM for testing | Yes (`aws acm import-certificate`). Imported certificates never renew. |
| CloudFront to a custom origin | No. The origin certificate must come from a trusted public CA. |
| Public browsers hitting a production site | No. Use an ACM public certificate. |

```bash
aws acm import-certificate --certificate fileb://cert.pem --private-key fileb://key.pem
```

### API Gateway client certificates

For REST APIs, API Gateway can generate a client certificate (`aws apigateway generate-client-certificate`) and present it to your HTTP backend. The backend checks it with the certificate's public key, so it accepts only calls that came through API Gateway. That is a different direction from mTLS on a custom domain, where API Gateway checks certificates presented by callers.

### Key pairs for signing in code

When a development workflow needs a signing key (for example to sign tokens or artifacts), create an asymmetric KMS key (`aws kms create-key --key-spec RSA_2048 --key-usage SIGN_VERIFY`) and call `Sign` and `Verify`. The private key stays in KMS, and `GetPublicKey` gives others the public half. Use `GenerateDataKeyPair` when the private key must exist outside KMS. See [2.2.4](2.2.4-kms-key-management.md#key-specs).

## Storing development keys

- Never commit private keys, `.pem` files, or certificates with keys to Git. Add them to `.gitignore`, and run secret scanning in CI (see [1.1.9](../../domain-1-development-with-aws-services/task-1.1-build-application-code/1.1.9-ai-assisted-development-tools.md)).
- Shared team keys belong in Secrets Manager or Parameter Store `SecureString`, with IAM controlling who can read them ([2.2.7](2.2.7-secrets-management.md)).
- Never bake private keys into AMIs or container images. Anyone who can pull the image gets the key.
- Rotate or delete keys when people leave a project; Session Manager and Instance Connect make this unnecessary because access follows IAM.

## Exam triggers

| Scenario clue | Answer | Why the alternatives are wrong |
|---|---|---|
| "Local HTTPS for testing" | Self-signed certificate with OpenSSL | ACM public certificates can't be issued for `localhost` or installed locally |
| "Avoid distributing SSH keys; no inbound port 22; audit sessions" | Session Manager | Instance Connect still needs port 22 |
| "Temporary SSH access controlled by IAM" | EC2 Instance Connect (60-second key) | Shared key pairs can't be revoked per person |
| "Instance Connect fails" | Security group doesn't allow port 22 from the source | The temporary key is pushed automatically |
| "Use my existing SSH key with EC2" | `aws ec2 import-key-pair` with the public key | Uploading the private key is never needed |
| "Lost the .pem file for a running instance" | Add a new public key through Session Manager, Instance Connect, or by editing the volume | AWS doesn't keep the private key |
| "Where does CloudFormation put the private key of a new key pair?" | Parameter Store `/ec2/keypair/<key_pair_id>` | It isn't returned in stack outputs |
| "Realistic internal TLS and mTLS in dev and test accounts" | AWS Private CA shared through RAM | Per-service self-signed certificates have no common trust or revocation |
| "Backend must only accept requests from API Gateway" | API Gateway generated client certificate | API keys identify clients but aren't authentication |

## Common traps

- Thinking AWS can resend the private key of an EC2 key pair. It returns it once.
- Thinking EC2 Instance Connect removes the need for port 22. Session Manager is the no-inbound-port option.
- Using a self-signed certificate on a CloudFront custom origin.
- Generating a certificate without a SAN and wondering why browsers reject it.
- Using `curl -k` or disabling verification in code to "fix" a dev certificate. Trust the certificate instead.
- Committing keys, or baking them into images, for convenience.
- Expecting an imported test certificate in ACM to renew.

## Quick recall

- `ssh-keygen -t ed25519`; `chmod 400` the private key.
- `create-key-pair` returns the private key once; `import-key-pair` takes only your public key.
- ED25519 key pairs don't work for Windows instances.
- CloudFormation `AWS::EC2::KeyPair` stores the private key in Parameter Store under `/ec2/keypair/`.
- Session Manager: no SSH keys, no open ports, IAM plus logging.
- Instance Connect: 60-second temporary key, port 22 still required.
- `openssl req -x509 ... -addext subjectAltName=...` = self-signed; `openssl req -new` = CSR.
- ALB accepts self-signed target certificates; CloudFront custom origins don't.
- Realistic dev certificates: AWS Private CA.
