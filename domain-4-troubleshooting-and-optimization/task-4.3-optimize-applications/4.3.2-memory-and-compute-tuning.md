# 4.3.2 Tune application memory and compute capacity

**Domain 4 · Task 4.3 · Skill 4.3.2** · [Task overview](README.md) · Previous: [4.3.1 Concurrency controls](4.3.1-concurrency-controls.md) · Next: [4.3.3 Messaging optimization](4.3.3-messaging-optimization.md)

## What the exam expects

This skill tests whether you can pick the right amount of memory and compute for a workload and prove it with numbers. The most common question is "should we raise or lower AWS Lambda memory", and the right answer depends on whether the function is CPU-bound (limited by its central processing unit, or CPU), memory-bound, or waiting on something else. Cost is not proportional to memory, because duration changes too. Questions also cover choosing Amazon Elastic Compute Cloud (EC2) instance families, AWS Graviton (arm64), AWS Fargate task sizes, Amazon DynamoDB capacity modes, and code-level changes that cut compute.

You must be able to:

- Read a Lambda `REPORT` line and decide whether more memory would help.
- Compute Lambda cost as memory × duration, and explain why more memory can cost less.
- Use AWS Lambda Power Tuning or AWS Compute Optimizer to find the cost-optimal memory setting.
- Know when arm64 lowers cost without code changes, and what must be checked first.
- Right-size EC2 instances and Fargate tasks, and decide between DynamoDB on-demand and provisioned capacity with numbers.
- Recognize code changes (batching, projections, `Query` instead of `Scan`) that cut compute and requests.

## Key terms

| Term | Meaning |
|---|---|
| CPU-bound | Time is spent computing. More CPU makes it faster. |
| I/O-bound | Time is spent waiting on a network call, disk, or another service. More CPU barely helps. |
| Memory-bound | The function is close to its memory limit, causing garbage collection pressure, swapping to `/tmp`, or out-of-memory errors. |
| GB-second | Lambda's compute billing unit: configured memory in GB × billed duration in seconds. |
| `Max Memory Used` | Peak memory of one invocation, reported in the `REPORT` log line. |
| Right-sizing | Matching instance, task, or function size to measured use. |
| AWS Lambda Power Tuning | An open-source tool that runs a function at several memory settings through an AWS Step Functions state machine and charts cost against duration. |
| Graviton (arm64) | AWS-designed Arm processors. Lambda's `arm64` architecture runs on them. |
| Burstable instance | An EC2 T-family instance that earns CPU credits while idle and spends them under load. |

## Lambda memory and CPU

- Memory is configurable from 128 MB to 10,240 MB in 1 MB steps. Default 128 MB.
- CPU, and network bandwidth, scale in proportion to memory. At 1,769 MB a function has the equivalent of one virtual CPU (vCPU). The maximum is 6 vCPUs at 10,240 MB. Older material says 1,792 MB; current documentation says 1,769 MB.
- There is no separate CPU setting. More memory is the only way to get more CPU.
- Above one vCPU, single-threaded code gains nothing more. Code must use multiple threads or processes to benefit.

### Cost math

```
Compute cost per invocation ≈ memory (GB) × billed duration (s) × price per GB-second
Total = compute cost + request charge
```

Illustrative CPU-bound workload from the domain sources:

| Memory | Duration | GB × seconds | Relative cost |
|---|---|---|---|
| 128 MB | 4.0 s (CPU-starved) | 0.125 × 4.0 | 0.50 |
| 512 MB | 1.1 s | 0.5 × 1.1 | 0.55 |
| 1,024 MB | 0.55 s | 1.0 × 0.55 | 0.55 |
| 1,769 MB (one vCPU) | 0.32 s | 1.73 × 0.32 | 0.55 |
| 3,008 MB | 0.30 s (no longer CPU-bound) | 2.94 × 0.30 | 0.88 |

Through the CPU-bound range, total cost stays roughly flat while latency drops eightfold, so the faster setting is nearly free. Past the point where the code stops being CPU-bound (about one vCPU here for single-threaded code), extra memory only adds cost. Never answer a memory question from the memory number alone; reason about the duration change it causes.

```mermaid
flowchart LR
    LOW[128 MB<br/>slow, CPU-starved] -->|raise memory| ELBOW[Elbow: cost flat or lower,<br/>duration much shorter]
    ELBOW -->|raise further| HIGH[Diminishing returns:<br/>duration flat, cost climbs]
```

### Reading the evidence

Every invocation writes a `REPORT` line to Amazon CloudWatch Logs:

```
REPORT RequestId: 9f2...  Duration: 3920.40 ms  Billed Duration: 3921 ms
Memory Size: 128 MB  Max Memory Used: 121 MB
```

| Evidence | Diagnosis | Action |
|---|---|---|
| High `Duration`, high CPU (CloudWatch Lambda Insights `cpu_total_time` close to duration) | CPU-bound | Raise memory, re-measure duration and cost |
| `Max Memory Used` close to `Memory Size`, or out-of-memory errors | Memory-bound | Raise memory; check for leaks across warm invocations |
| High `Duration`, low CPU, low memory | I/O-bound, waiting on a dependency | Trace the slow call with AWS X-Ray ([4.3.5](4.3.5-performance-bottleneck-detection.md)); memory will not help |
| Slow only on some invocations, `Init Duration` present | Cold start | Mitigate per [4.3.1](4.3.1-concurrency-controls.md#cold-starts-prove-it-then-mitigate) |
| `Max Memory Used` far below `Memory Size`, duration unchanged when you lower memory | Over-provisioned | Lower memory and confirm duration does not regress |
| Intermittent timeouts under load, CPU near 100% the whole time | CPU-starved | Raise memory, not only the timeout |

Raising only the timeout lets slow code run longer and bills more duration without fixing anything. Lowering memory on a CPU-bound function can raise total cost, because duration grows faster than the rate falls.

### Finding the optimal setting

| Tool | How it works | Use it when |
|---|---|---|
| AWS Lambda Power Tuning | Open-source Step Functions state machine you deploy. It invokes the function at each memory value you list, with a representative payload, and charts cost against speed. Can run in a continuous integration and continuous delivery (CI/CD) pipeline. | Before launch or after code changes; you want measured numbers for your payload |
| AWS Compute Optimizer | Analyzes historical CloudWatch metrics and recommends a memory size with estimated cost difference | Ongoing review of many functions already in production |
| CloudWatch Lambda Insights | Extension layer that reports CPU time, memory, network, and init duration per function | You need the CPU and memory detail behind a recommendation |
| Manual test | Invoke at two or more settings and compare `Billed Duration` × memory | Quick check, as in [Lab 1](labs.md) |

Power Tuning reading: if cost and duration both fall from 128 MB to 512 MB, and past 1,024 MB duration drops only slightly while cost rises, the function was CPU-starved below 512 MB. Set memory near the bottom of the cost curve (here 512 to 1,024 MB), or slightly above if latency matters more than cost.

> **Not on the DVA-C03 service list.** AWS Compute Optimizer is not named in the in-scope list. It uses machine learning over CloudWatch utilization history to recommend Lambda memory, EC2 instance types, Auto Scaling group configurations, Amazon Elastic Block Store (EBS) volumes, and Amazon Elastic Container Service (ECS) on Fargate task sizes. Findings classify a resource as under-provisioned, over-provisioned, or optimized. Recommendations reflect past use only, so check them against planned growth and burst headroom before applying. It is covered with the other artificial intelligence (AI) and machine learning optimization tools in [4.3.6](4.3.6-ai-assisted-optimization.md).

### arm64 (Graviton)

- Lambda offers `x86_64` and `arm64`. AWS states Graviton-based functions can get up to 34% better price performance, and the arm64 price per GB-second is lower than x86_64 (about 20% in most Regions; verify on the pricing page).
- Interpreted code (Python, Node.js) often runs unchanged. Before switching, confirm every native dependency, layer, and extension has an arm64 build, and rebuild container images for arm64.
- Test performance on arm64 and compare before moving production. The architecture is set per function version.
- "Reduce Lambda cost with no code change" points to arm64 when dependencies support it. Graviton does not shorten cold starts the way SnapStart does; it lowers warm-path compute cost.

### Other Lambda compute levers

- **Init work:** move one-time setup (SDK clients, configuration, models) outside the handler so warm invocations skip it. Lazy-load modules that only some requests need.
- **Package size:** smaller zips and images start faster ([3.3.1](../../domain-3-testing-and-deployment/task-3.3-deploy-with-ci-cd/3.3.1-lambda-packaging.md)).
- **Ephemeral storage:** `/tmp` is configurable from 512 MB to 10,240 MB, separately from memory. Raise it for large file processing instead of raising memory.
- **Avoid unnecessary calls:** cache configuration and secrets across warm invocations ([4.3.4](4.3.4-caching-for-performance.md#in-function-caching-in-lambda)).
- **Right tool:** a sustained, constant workload with no idle time (for example the equivalent of 2 vCPU and 4 GB busy around the clock) can cost less on EC2 or Fargate than on Lambda. Model both.

## EC2 and container compute

| Need | Choice |
|---|---|
| General web and app servers | General purpose (M family) |
| CPU-heavy batch, encoding, high request rates | Compute optimized (C family) |
| In-memory caches, large heaps, analytics | Memory optimized (R, X families) |
| Spiky, mostly idle workloads | Burstable (T family). Running out of CPU credits throttles the instance, or bills extra in unlimited mode |
| Lower cost for compatible software | Graviton instance types (names ending in `g`, such as `m7g`) |

- **Vertical vs horizontal:** scaling up (bigger instance) suits databases and other non-distributed systems; scaling out (more instances through an Auto Scaling group) suits stateless app tiers. See [4.3.1](4.3.1-concurrency-controls.md#ec2-auto-scaling).
- **Memory is not a default EC2 metric.** CloudWatch reports CPU, network, and disk by default, but memory use requires the CloudWatch agent publishing a custom metric. Right-sizing recommendations based on memory need that agent.
- **Fargate:** you choose task CPU and memory from supported combinations. Over-sized tasks waste money; under-sized ones get CPU throttled or killed for exceeding memory. Watch per-task CPU and memory in CloudWatch Container Insights.
- **ECS on EC2:** task placement strategies such as `binpack` on memory or CPU pack tasks onto fewer instances to cut cost; `spread` across Availability Zones favors availability.

## DynamoDB capacity

DynamoDB throughput is compute capacity you choose. Capacity unit math and key design are in [1.3.4](../../domain-1-development-with-aws-services/task-1.3-use-data-stores/1.3.4-dynamodb-design-and-operations.md#capacity-modes).

| Mode | Fits | Watch out for |
|---|---|---|
| On-demand | Unknown, spiky, or new workloads; no capacity planning | Can still throttle on hot partitions, on sudden spikes well beyond the previous peak, and at table quotas |
| Provisioned with auto scaling | Steady, predictable traffic with high utilization | Auto scaling reacts with some lag; burst capacity covers short spikes only |

- On-demand prices dropped by 50% in November 2024, so older material calling it "much more expensive" is out of date. Provisioned can still be cheaper for steady, well-utilized traffic.
- Decide with data: compare the on-demand bill with what provisioned capacity at the observed consumed read and write capacity (CloudWatch `ConsumedReadCapacityUnits` and `ConsumedWriteCapacityUnits`) plus headroom would have cost.
- Switching is limited: provisioned to on-demand up to 4 times in a rolling 24 hours; on-demand to provisioned at any time.
- If throttling is concentrated on one key, more capacity does not fix it. That is a hot partition; see [4.3.5](4.3.5-performance-bottleneck-detection.md#dynamodb-throttling-hot-key-or-capacity).

## Code-level efficiency

The cheapest compute is the work you do not do.

| Inefficiency | Fix |
|---|---|
| One application programming interface (API) call per item in a loop | Batch APIs: `BatchGetItem` (up to 100 items), `BatchWriteItem` (up to 25 puts or deletes), Amazon Simple Queue Service (SQS) `SendMessageBatch` (up to 10), Amazon Kinesis `PutRecords` (up to 500) |
| N+1 queries (one query for a list, then one per row) | A single query with a better key or index, or a batch read |
| `Scan` with a filter to find a few items | `Query` on a key or a global secondary index (GSI). A filter expression still reads, and bills, every scanned item |
| Reading whole items for one attribute | `ProjectionExpression` to return only needed attributes (smaller responses; read units are still charged on the full item size) |
| Sequential independent calls | Run them in parallel with async I/O or a bounded thread pool ([4.3.1](4.3.1-concurrency-controls.md#thread-pools)) |
| Large payloads over the network | Compress them, or pass an S3 reference instead |
| Retrying without backoff | Exponential backoff with jitter ([1.1.3](../../domain-1-development-with-aws-services/task-1.1-build-application-code/1.1.3-resilience-retries-and-backoff.md)); retry only `UnprocessedItems` or `UnprocessedKeys` from batch calls |
| Recursive or chained synchronous Lambda calls | Step Functions or a queue between steps |

## Worked scenarios

**Fix the right layer.** A checkout API's p99 latency rose from 200 ms to 4 s after an infrastructure deployment. X-Ray shows the time in the DynamoDB subsegment, and the table's `ThrottledRequests` is above 0 with consumed read capacity pinned at the provisioned limit. CloudTrail shows the deployment switched the table from on-demand to provisioned with low read capacity. The fix is the table's capacity (back to on-demand, or right-sized provisioned capacity with auto scaling), plus optionally DynamoDB Accelerator (DAX) for repeated hot reads. Raising the Lambda function's memory would cost more and fix nothing, because the function was waiting, not computing.

**CPU-bound image resizing.** An image-resizing function at 128 MB times out intermittently under load, and CPU stays near 100% for each invocation. Raise memory to give it more CPU; run Power Tuning to pick the value. Raising only the timeout, lowering memory, or adding a cache does not address CPU starvation.

**Over-provisioned function.** A cost review shows a function configured at 3,008 MB whose `Max Memory Used` never exceeds 300 MB. Lower memory in steps and re-measure. If duration stays flat (I/O-bound work), the lower setting is cheaper. If duration grows enough to offset the lower rate, the function was using the CPU, and the higher setting was justified.

**Payment function "slow under load".** Check `Max Memory Used`, CPU, and duration together. High CPU and high duration point to more memory. Low CPU and high duration point to a downstream wait; trace it before touching memory.

## Exam triggers

| Scenario clue | Answer | Why the alternatives are wrong |
|---|---|---|
| CPU-heavy Lambda is slow or times out | Increase memory (CPU scales with it) | Raising only the timeout runs the same slow code longer; there is no CPU setting |
| Find the cost-optimal Lambda memory | Lambda Power Tuning or Compute Optimizer | Guessing from the memory number ignores duration |
| Cut Lambda cost with no code change | Switch to arm64 after checking dependencies | Lowering memory can raise cost for CPU-bound code |
| High duration, low CPU and memory use | I/O-bound; trace the downstream call | More memory does not speed up waiting |
| `Max Memory Used` near the configured limit | Raise memory | Raising the timeout does not prevent out-of-memory errors |
| EC2 memory metrics missing for right-sizing | Install the CloudWatch agent | Detailed monitoring adds 1-minute metrics, not memory |
| Steady, predictable DynamoDB traffic, high on-demand bill | Model provisioned capacity with auto scaling from consumed-capacity metrics | "Provisioned is always cheaper" and "on-demand is always optimal" are both wrong |
| Many single-item calls in a loop | Batch APIs | More concurrency multiplies the request cost |
| `Scan` with a filter to find a few items is slow and costly | `Query` on a key or GSI | A filter expression does not reduce read capacity consumed |

## Common traps

- Treating cost as proportional to memory. Cost is memory × duration.
- Raising memory for every slow function. It helps CPU-bound and memory-bound code only.
- Raising the timeout instead of fixing CPU starvation.
- Expecting more than one vCPU to help single-threaded code.
- Applying Compute Optimizer or AI recommendations without checking upcoming load and burst needs.
- Switching to arm64 without verifying native dependencies, layers, and extensions.
- Believing DynamoDB on-demand cannot throttle.
- Thinking `ProjectionExpression` or a filter expression lowers read capacity consumed. They reduce the data returned, not the data read.

## Quick recall

- Lambda memory 128 MB to 10,240 MB; 1,769 MB = one vCPU; up to 6 vCPUs.
- Cost = GB × seconds × rate, plus requests. CPU-bound code is often no more expensive with more memory.
- `Max Memory Used` near the limit means raise memory; far below and flat duration means lower it.
- Power Tuning = Step Functions that test memory settings; Compute Optimizer = recommendations from history.
- arm64 = up to 34% better price performance; check native builds.
- `/tmp` scales separately (512 MB to 10,240 MB).
- EC2 memory needs the CloudWatch agent.
- Batch APIs: `BatchGetItem` 100, `BatchWriteItem` 25, `SendMessageBatch` 10, `PutRecords` 500.
- `Query` over `Scan`; filters and projections do not cut read units.
