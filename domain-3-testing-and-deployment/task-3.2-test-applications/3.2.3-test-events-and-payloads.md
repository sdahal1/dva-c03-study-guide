# 3.2.3 Create representative test events, including JSON payloads for Lambda functions and API Gateway APIs

**Domain 3 · Task 3.2 · Skill 3.2.3** · [Task overview](README.md) · Previous: [3.2.2 Mock APIs](3.2.2-mock-apis.md) · Next: [3.2.4 Isolated test environments](3.2.4-isolated-test-environments.md)

## What the exam expects

This skill tests whether you can drive a Lambda function or an API Gateway method with an input that looks like the real thing, without wiring up the real event source. Questions describe a trigger (an S3 upload, an Amazon Simple Queue Service or SQS message, an API request, a DynamoDB stream record) and ask how to simulate it, or show a handler that fails on real traffic because the test payload had the wrong shape. Wrong answers provision real infrastructure for every test, test only in production, or claim that a trigger cannot be simulated.

You must be able to:

- Create and share Lambda console test events, and invoke functions with test payloads from the AWS command line interface (CLI) and the AWS Serverless Application Model (AWS SAM) CLI.
- Generate sample events for common sources with `sam local generate-event`.
- Test an API Gateway REST API method from the console or with `test-invoke-method`, and know that it calls the real backend.
- Recognize the JavaScript Object Notation (JSON) structure of API Gateway, SQS, Amazon Simple Notification Service (SNS), S3, Kinesis, DynamoDB Streams, and EventBridge events, and the parsing mistakes each one invites.
- Validate an EventBridge event pattern offline with `test-event-pattern`.

## Key terms

| Term | Meaning |
|---|---|
| Test event | A JSON document passed to a function's handler as the `event` argument. |
| Private test event | A Lambda console test event visible only to its creator. Up to 10 per function. |
| Shareable test event | A Lambda console test event visible to other users in the account, stored in an EventBridge schema registry. |
| Event template | A prebuilt sample payload for a source (S3 Put, SQS, API Gateway proxy), offered by the console and by `sam local generate-event`. |
| Proxy event | The event API Gateway sends to Lambda with a proxy integration: the whole HTTP request as JSON. |
| Payload format version | The proxy event layout: 1.0 for REST APIs (and optional for HTTP APIs), 2.0 by default for HTTP APIs. |
| Fixture | A saved test input, such as `events/s3-put.json`, checked into the repository. |

## Ways to send a test event

| Tool | What runs | Calls real AWS? | Best for |
|---|---|---|---|
| Lambda console Test tab | The deployed function, invoked synchronously | Yes | Quick manual checks during development |
| `aws lambda invoke --payload` | The deployed function or a specific version or alias | Yes | Scripts, smoke tests, async invocation tests |
| `sam local invoke -e event.json` | The handler in a local container | Only if the code calls AWS | Local handler testing before deploy |
| `sam local generate-event` | Nothing; prints a sample event | No | Creating realistic fixtures |
| `sam remote invoke` and `sam remote test-event` | The deployed function, with local or shared events | Yes | Cloud testing, team-shared events |
| API Gateway console Test tab or `test-invoke-method` | The REST API method and its real integration, without a stage deployment | Yes | Debugging mapping and integration behavior |
| `aws events test-event-pattern` | Nothing; compares an event with a rule pattern | No | Validating EventBridge rules offline |
| Calling the handler in a unit test | Your handler function in-process | No (with mocks) | Automated tests in continuous integration (CI) |

Console test events are manual checks. They are useful while developing but do not replace a repeatable, automated test suite that runs in the pipeline.

## Lambda console test events

When you choose **Test**, Lambda invokes the function **synchronously** with the test event, and the runtime passes the parsed JSON to the handler. You can pick a template (S3 Put, SQS, SNS, API Gateway proxy, DynamoDB Streams, Kinesis, EventBridge, Amazon Cognito triggers, and others), edit it, and save it.

| | Private | Shareable |
|---|---|---|
| Who sees it | Only the creator | Users in the same account |
| Limit | Up to 10 per function | Stored as schemas |
| Storage | With the function, for that user | EventBridge schema registry named `lambda-testevent-schemas` |
| Extra permissions | None | EventBridge schema registry actions (`schemas:CreateRegistry`, `schemas:CreateSchema`, `schemas:DescribeSchema`, `schemas:UpdateSchema`, and others) |
| Use from SAM | No | `sam remote test-event` |

If a teammate cannot see shareable test events, check their permissions for the schema registry actions and any resource-based policy on the registry. Deleting a function does not delete its shareable test event schemas.

## Invoke with the AWS CLI

```bash
# Synchronous invoke with a payload file (AWS CLI v2)
aws lambda invoke --function-name orders-fn \
  --cli-binary-format raw-in-base64-out \
  --payload file://events/api-post.json \
  out.json
cat out.json

# Invoke a specific alias or version
aws lambda invoke --function-name orders-fn --qualifier prod \
  --cli-binary-format raw-in-base64-out --payload file://events/api-post.json out.json

# Asynchronous invoke: returns 202 immediately; retries and destinations apply
aws lambda invoke --function-name orders-fn --invocation-type Event \
  --cli-binary-format raw-in-base64-out --payload file://events/sqs.json out.json

# Return the last 4 KB of the execution log, base64-encoded
aws lambda invoke --function-name orders-fn --log-type Tail \
  --cli-binary-format raw-in-base64-out --payload '{"ping": true}' out.json \
  --query 'LogResult' --output text | base64 --decode
```

- AWS CLI v2 treats `--payload` as base64 by default. Add `--cli-binary-format raw-in-base64-out` to pass raw JSON with `file://` or inline. Without it, the call fails with an invalid base64 error.
- `--invocation-type DryRun` checks permissions and parameters without running the function.
- `--log-type Tail` works only for synchronous invocations.

How invocation type changes retries and failure handling is covered in [1.2.3](../../domain-1-development-with-aws-services/task-1.2-develop-lambda-functions/1.2.3-lambda-invocation-lifecycle-and-failures.md).

## Generate and use events with AWS SAM

`sam local generate-event <service> <event-type>` prints a sample event, with flags to customize common fields:

```bash
sam local generate-event --help                       # list services
sam local generate-event s3 put --bucket my-bucket --key "uploads/photo 1.jpg" > events/s3-put.json
sam local generate-event apigateway aws-proxy --method POST --path orders --body '{"item":"widget"}' > events/api-post.json
sam local generate-event apigateway http-api-proxy > events/http-api.json
sam local generate-event sqs receive-message --body '{"orderId":"o-1"}' > events/sqs.json
sam local generate-event sns notification --message "hello" > events/sns.json
sam local generate-event dynamodb update > events/ddb-stream.json
sam local generate-event kinesis get-records --data "hello" > events/kinesis.json
sam local generate-event cloudwatch scheduled-event > events/schedule.json

# Run locally
sam local invoke OrdersFunction -e events/api-post.json
sam local generate-event s3 put --bucket b --key k | sam local invoke ImageFunction -e -

# Run against the deployed function
sam remote invoke OrdersFunction --stack-name orders-dev --event-file events/api-post.json

# Share an event with the team (stored with the function's shareable test events)
sam remote test-event put OrdersFunction --stack-name orders-dev --name big-order --file events/api-post.json
sam remote test-event list OrdersFunction --stack-name orders-dev
sam remote invoke OrdersFunction --stack-name orders-dev --test-event-name big-order
```

Keep fixtures in an `events/` folder in the repository so local runs, CI tests, and teammates use the same inputs.

## API Gateway console test

For a REST API, the console's **Test** tab on a method (and the `test-invoke-method` API) sends a request through the method without deploying the API to a stage. You supply path, query string, headers, and body, and see the status, latency, response body and headers, and **simulated** CloudWatch Logs showing the request and response after each mapping step.

```bash
aws apigateway test-invoke-method \
  --rest-api-id abc123 --resource-id def456 --http-method POST \
  --path-with-query-string '/orders?debug=true' \
  --headers '{"Content-Type": "application/json"}' \
  --body '{"item": "widget", "quantity": 2}'
```

- The integration call is real. A test of a `DELETE` method deletes the data. Only the logs are simulated.
- Test invocations are a REST API feature. HTTP APIs do not have them; test an HTTP API by calling its stage URL (uniform resource locator) (auto-deploy makes changes live on the `$default` stage).
- The status code and body you see can differ from what Lambda returned, because mapping templates and integration responses apply.

## Event shapes to recognize

Most test-event bugs are shape bugs: the handler was tested with a payload that does not match what the source really sends. Generate fixtures from templates rather than writing them from memory.

### API Gateway REST API proxy event (payload format 1.0)

```json
{
  "resource": "/orders/{id}",
  "path": "/orders/o-1",
  "httpMethod": "POST",
  "headers": {"Content-Type": "application/json"},
  "multiValueHeaders": {"Content-Type": ["application/json"]},
  "queryStringParameters": null,
  "pathParameters": {"id": "o-1"},
  "stageVariables": {"lambdaAlias": "dev"},
  "requestContext": {"stage": "dev", "requestId": "c6af9ac6-...", "identity": {"sourceIp": "203.0.113.10"}},
  "body": "{\"item\":\"widget\",\"quantity\":2}",
  "isBase64Encoded": false
}
```

### HTTP API proxy event (payload format 2.0)

```json
{
  "version": "2.0",
  "routeKey": "POST /orders",
  "rawPath": "/orders",
  "rawQueryString": "debug=true",
  "headers": {"content-type": "application/json"},
  "queryStringParameters": {"debug": "true"},
  "requestContext": {"http": {"method": "POST", "path": "/orders", "sourceIp": "203.0.113.10"}, "stage": "$default"},
  "body": "{\"item\":\"widget\"}",
  "isBase64Encoded": false
}
```

A Lambda proxy integration must return `statusCode` and a **string** `body`; returning an object body produces a 502. See [1.2.4](../../domain-1-development-with-aws-services/task-1.2-develop-lambda-functions/1.2.4-lambda-service-integrations.md).

### SQS, SNS, and S3 events

```json
{"Records": [{
  "messageId": "059f36b4-87a3-44ab-83d2-661975830a7d",
  "receiptHandle": "AQEBwJnKyrHigUMZj6rYigCgxlaS3SLy0a...",
  "body": "{\"orderId\":\"o-1\"}",
  "attributes": {"ApproximateReceiveCount": "1", "SentTimestamp": "1545082649183"},
  "messageAttributes": {},
  "eventSource": "aws:sqs",
  "eventSourceARN": "arn:aws:sqs:us-east-1:111122223333:orders-queue"
}]}
```

```json
{"Records": [{
  "EventSource": "aws:sns",
  "Sns": {"Subject": "order", "Message": "{\"orderId\":\"o-1\"}", "MessageAttributes": {}}
}]}
```

```json
{"Records": [{
  "eventSource": "aws:s3",
  "eventName": "ObjectCreated:Put",
  "s3": {
    "bucket": {"name": "my-bucket", "arn": "arn:aws:s3:::my-bucket"},
    "object": {"key": "uploads/photo+1.jpg", "size": 1024}
  }
}]}
```

### Kinesis, DynamoDB Streams, and EventBridge events

```json
{"Records": [{
  "eventSource": "aws:kinesis",
  "kinesis": {"partitionKey": "o-1", "sequenceNumber": "4959...", "data": "eyJvcmRlcklkIjoiby0xIn0="}
}]}
```

```json
{"Records": [{
  "eventName": "MODIFY",
  "eventSource": "aws:dynamodb",
  "dynamodb": {
    "Keys": {"id": {"S": "o-1"}},
    "OldImage": {"id": {"S": "o-1"}, "status": {"S": "PENDING"}},
    "NewImage": {"id": {"S": "o-1"}, "status": {"S": "SHIPPED"}},
    "StreamViewType": "NEW_AND_OLD_IMAGES"
  }
}]}
```

```json
{
  "version": "0",
  "id": "6a7e8feb-b491-4cf7-a9f1-bf3703467718",
  "detail-type": "Order Shipped",
  "source": "com.example.orders",
  "account": "111122223333",
  "time": "2026-12-01T12:00:00Z",
  "region": "us-east-1",
  "resources": [],
  "detail": {"orderId": "o-1", "carrier": "UPS"}
}
```

### Parsing mistakes each shape invites

| Source | Field | Mistake | Fix |
|---|---|---|---|
| API Gateway proxy | `body` | Treating it as an object | `json.loads(event["body"] or "{}")`; decode base64 first when `isBase64Encoded` is true |
| API Gateway REST proxy | `queryStringParameters` | Assuming a dict; it is `null` with no query string | `(event.get("queryStringParameters") or {})` |
| API Gateway | REST 1.0 vs HTTP 2.0 | Reading `httpMethod` from a 2.0 event | 2.0 uses `requestContext.http.method` and `rawPath` |
| SQS, SNS, S3, Kinesis, Streams | `Records` | Processing only `Records[0]` | Loop over every record; a batch can hold many |
| SQS | `body` | Treating it as an object | It is a string; parse it |
| SNS | `Sns.Message` | Treating it as an object | It is a string; parse it |
| S3 | `object.key` | Using it directly | It is URL-encoded (spaces become `+`): `urllib.parse.unquote_plus(key)` |
| Kinesis | `kinesis.data` | Reading it as text | It is base64; decode, then parse |
| DynamoDB Streams | `NewImage` | Reading plain values | It is typed JSON (`{"S": "..."}`); use `TypeDeserializer` |
| EventBridge | `detail` | Parsing it as a string | It is already an object |

Serialization and deserialization in depth is [1.1.7](../../domain-1-development-with-aws-services/task-1.1-build-application-code/1.1.7-serialization-and-deserialization.md).

## Build a fixture-driven test suite

```python
# tests/test_events.py
import json
import pathlib
import pytest
from src.handler import handler

EVENTS = pathlib.Path(__file__).parent.parent / "events"

def load(name):
    return json.loads((EVENTS / name).read_text())

@pytest.mark.parametrize("fixture, expected_status", [
    ("api-post.json", 201),
    ("api-post-missing-body.json", 400),
    ("api-post-bad-json.json", 400),
])
def test_api_events(fixture, expected_status):
    assert handler(load(fixture), None)["statusCode"] == expected_status

def test_s3_key_is_url_decoded():
    event = load("s3-put.json")
    event["Records"][0]["s3"]["object"]["key"] = "uploads/photo+1.jpg"
    result = handler(event, None)
    assert result["key"] == "uploads/photo 1.jpg"
```

Include negative fixtures: missing fields, `null` query strings, malformed JSON bodies, base64-encoded bodies, oversized batches, and duplicate SQS messages (to test idempotency, since standard queues can deliver more than once and FIFO queues deduplicate only within a five-minute window).

Use synthetic data in fixtures. Do not copy production events that contain personally identifiable information (PII), tokens, or secrets into a repository. Masking and redaction are covered in [2.2.6](../../domain-2-security/task-2.2-encrypt-and-protect-sensitive-data/2.2.6-sensitive-data-detection-and-masking.md).

## Test EventBridge rule patterns offline

`aws events test-event-pattern` returns `true` or `false` for whether a sample event matches a pattern. Nothing is published and no target runs, so a pipeline can check both the events that should match and those that should not:

```bash
aws events test-event-pattern \
  --event-pattern '{"source": ["com.example.orders"], "detail-type": ["Order Shipped"], "detail": {"carrier": ["UPS", "FedEx"]}}' \
  --event file://events/order-shipped.json
# {"Result": true}
```

`put-events` publishes a real event to a live bus; `describe-rule` only returns the rule's configuration.

## Exam triggers

| Scenario clue | Answer | Why the alternatives are wrong |
|---|---|---|
| Simulate an S3 upload without uploading a file | S3 Put test event (console template or `sam local generate-event s3 put`) | Real uploads per test run are slow and add dependencies |
| Simulate an SQS-triggered invocation | Test event with the SQS `Records[].body` structure | A plain JSON body is not what Lambda receives from SQS |
| Teammates should reuse the same console test events | Shareable test events (EventBridge schema registry) | Private events are visible only to their creator |
| Teammate cannot see shareable test events | Grant the EventBridge schema registry permissions | Lambda permissions alone are not enough |
| Invoke with a JSON file from AWS CLI v2 fails with invalid base64 | Add `--cli-binary-format raw-in-base64-out` | The payload is not the problem |
| See the function's log output from a CLI invoke | `--log-type Tail`, then base64-decode `LogResult` (last 4 KB) | Logs are not in the response payload |
| Test a REST API method without deploying it to a stage | API Gateway console Test tab or `test-invoke-method` | Deploying a stage just to test is unnecessary |
| Test a `DELETE` method safely | Point the method at a test backend first; console tests call the real integration | Console tests are not dry runs |
| Handler works in tests but fails on real S3 keys with spaces | Decode the URL-encoded key | The bucket configuration is not the cause |
| Lambda behind API Gateway returns 502 with clean logs | Return a string `body` and a `statusCode` | Raising the timeout does not fix the response shape |
| Validate an EventBridge pattern in CI without publishing | `aws events test-event-pattern` | `put-events` publishes to a live bus |

## Common traps

- Console tests invoke synchronously. They do not exercise asynchronous retries, destinations, or event source mapping batching.
- API Gateway console tests call the real backend and are REST-only.
- `body` in API Gateway proxy events, SQS records, and `Sns.Message` are strings, not objects.
- S3 object keys arrive URL-encoded.
- REST API payload 1.0 and HTTP API payload 2.0 differ; a fixture for one does not test the other.
- A batch event can contain many records. Test with more than one.
- Never put real customer data or secrets in test fixtures.

## Quick recall

- Private test events: creator only, up to 10 per function. Shareable: account-wide, stored in the `lambda-testevent-schemas` registry.
- `aws lambda invoke` needs `--cli-binary-format raw-in-base64-out` for raw JSON in CLI v2.
- `--log-type Tail` returns the last 4 KB of logs, base64-encoded.
- `sam local generate-event s3 put | sam local invoke -e -`.
- `sam remote invoke --event-file` or `--test-event-name` runs against the deployed function.
- API Gateway console Test = real call, simulated logs, REST only, no stage deployment needed.
- S3 key URL-encoded; Kinesis data base64; Streams typed JSON; EventBridge `detail` is an object.
- `aws events test-event-pattern` validates rules offline.
